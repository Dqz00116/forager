## Description

本需求面向需要理解、调试并信任 agent 抓取行为的使用者。

问题：agent 每次 crawl 的决策过程与工具调用是一个黑盒。当出现"漏保存"、"误清空"、"意外行为"时，使用者无法判断根因究竟来自 LLM 的决策、工具本身的缺陷，还是外部干扰。

方案：为每一次 crawl 记录全量 trace（包含完整的 LLM prompt / response 以及每一次工具调用），并将其持久化到可查询的存储中，支持回放与统计。

产出：每一次 crawl 的行为完全可观测、可查询、可分析。

### 设计哲学

不求全面但求精细，第一性原理。可观测性是一切调试的前提：行为不可观测，每次异常都是黑盒只能靠猜；行为可观测，根因直接可见。

### 背景

pi-crawler 已具备"取 / 懂 / 存"三本质内核（P1）。真实站点测试暴露了问题（extract 成功却没有 save 落盘、records.jsonl 被清空），但因缺乏行为记录，排查只能靠推断。本特性即 P2 可观测性：让每次 crawl 的完整行为可记录、可回放、可查询。本需求在现有项目基础上演进。

## Acceptance Criteria

- [ ] 每次 crawl 运行产生一条独立的运行记录，包含入口 URL、任务描述、开始/结束时间、最终状态
- [ ] 运行过程中的每次 LLM 交互被记录，含完整 prompt 与完整 response（全量，不截断决策依据）
- [ ] 运行过程中的每次工具调用被记录，含工具名、输入参数、输出结果/错误、耗时、是否导致落盘
- [ ] trace 数据持久化到 SQLite，跨运行保留、可按运行/工具/时间查询
- [ ] 提供查询能力：能查出"哪些运行中 extract 有产出但没有后续 save"这类行为模式
- [ ] trace 记录不影响 crawl 主流程：记录失败不导致抓取失败（可观测性旁路）
- [ ] CLI 结束时打印本次 trace 标识与查询入口
- [ ] 通过 trace 能直接回答此前的两个悬案：(a) GitHub Trending 为何 extract 后无 save；(b) records.jsonl 是否被 crawl 流程清空
- [ ] 全部测试真实运行、禁 mock，npm test 一键通过

## Notes

- 约束：Node >= 22.19、使用真实 LLM、禁止 mock、不得破坏现有"取 / 懂 / 存"内核。
- trace 含完整 prompt / response（用户明确要求全量，接受因此带来的较大存储开销与潜在的页面敏感内容）。
- SQLite 采用轻量嵌入式方案。
- P2 明确不含：自适应造工具、元工具、Docker——这些属于后续阶段。
- 已知限制：全量 trace 会显著增大存储占用；trace 中可能包含页面敏感内容，需使用者自行注意。
